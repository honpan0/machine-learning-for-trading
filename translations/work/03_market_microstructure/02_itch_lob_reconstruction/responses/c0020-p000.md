## 3. 委託簿重建演算法

### 兩種結構，以及為何兩者皆不可少

重建過程維護一個**委託池**與一個**委託簿**。委託池將每個有效委託參考編號對應至其買賣方向、價格與*剩餘*股數。委託簿則將每個價格對應至買賣兩側各自在該價位的總掛單股數：

```
pool = {order_ref: (side, price, shares_remaining), ...}
book = {
    "B": {price: total_shares, ...},  # bids
    "S": {price: total_shares, ...},  # asks
}
```

僅靠委託簿無法處理訊息，因為 `D` 與 `E` 指明的是委託，而非價格。僅靠委託池，則必須掃描才能得知最佳買賣報價。因此，每則訊息都會先讀取委託池，找到其作用的價位，再調整委託簿上的股數：

| 訊息 | 委託池 | 委託簿 |
|---|---|---|
| `A`／`F` 新增 | 記錄新委託 | 在該價格加入其股數 |
| `D` 刪除 | 移除委託 | 扣除其全部剩餘股數 |
| `X` 取消 | 減少剩餘股數 | 扣除已取消的股數 |
| `E` 成交執行 | 減少剩餘股數 | 扣除已成交的股數 |
| `C` 附價格的成交執行 | 減少剩餘股數 | 在原掛單價格扣除這些股數 |
| `U` 替換 | 使舊參考編號失效，記錄新編號 | 在舊價格扣除，在新價格加入 |

追蹤剩餘股數，才能正確處理 `D`。一筆新增時為 500 股、已成交 300 股的委託，在委託簿上剩下 200 股，刪除時必須移除 200 股。若重建時扣除原始的 500 股，就會使該價位的股數變成負值。

`reconstruct_lob_with_ofi` 在 `limit_orderbook` 中以編譯後的迴圈完成此工作，而 `14_itch_bar_sampling` 也呼叫相同模組。
