- **寫入**（`time_write`）——對本次執行新建的資料表進行單次寫入，不先暖機。每個資料集只會大量載入一次，因此量測的就是這次操作。重複執行會讓僅能附加的引擎加入重複資料列，或需要進行不屬於寫入操作的清除重建。
- **寫入長條呈現的是用戶端付出的成本，而各用戶端並不相同。** SQLite、DuckDB、ClickHouse 與 kdb+ 以一整塊資料接收追蹤資料（`to_sql`、Parquet 掃描、`insert_df`、`set`）。PostgreSQL 與 TimescaleDB 必須為每列建立一個 Python 元組，供 `execute_values` 使用；InfluxDB 則須為每列建立一個 `Point`，供行協定使用。建立這些物件是使用該介面的成本，因此保留在計時區間內；這三者也都會另外量測這項成本並印出占比，彙整於圖表上方的表格。這三個數字僅涵蓋*明確寫出的*資料列建構，不含其他成本。每個用戶端都會在某處轉換與序列化資料：`to_sql` 仍須逐列準備並綁定，`insert_df` 仍須序列化資料框；從外部無法分離這些工作，因此未標示量測占比的長條，並不代表全是引擎本身的成本。每根寫入長條都應解讀為「透過此引擎的 Python 用戶端，將這份追蹤資料寫入引擎的成本」，絕不能視為引擎的資料匯入速率。
- **計時區間包含持久化。** PostgreSQL 與 TimescaleDB 同步提交，因此其刷新至儲存裝置的成本包含在計時呼叫中。QuestDB（ILP + WAL）與 InfluxDB 會在資料列可供查詢之前就回覆確認，因此在計時呼叫*內部*透過 `wait_until_rows_visible` 輪詢，直到首次可查詢。如此，每個寫入時間都在同一事件發生時結束：資料已持久保存且可讀取。
- **讀取、彙總與連接**（`time_read`）——先進行一次不計時的暖機，再取 `TIMING_RUNS` 次執行的平均值。**這些都是暖快取數據**，作業系統頁面快取與各伺服器緩衝池皆然，會讓所有具有快取的引擎顯得有利。用戶端無法清空伺服器快取，因此在此進行「冷」讀取，會讓嵌入式引擎處於冷快取狀態，伺服器卻仍是暖快取，既非全冷，也無從比較。統一採暖快取是可量測的選擇；§2.4 在報告這些數據時也有說明。
- **每次讀取都會驗證**是否與預期資料列數完全一致。下方每個查詢的結果都具確定性，執行前就已知道答案，因此差一點仍是錯誤答案，不能接受；否則，默默傳回截斷結果的查詢，反而可能在圖中取得最快時間。
