1. **儲存配置決定掃描成本。** 將同欄資料存放在一起、並以批次執行的引擎，讀取分鐘追蹤資料的方式，不同於將同列資料存放在一起、為了回答兩個欄位的問題卻必須存取全部九個欄位的引擎。這種區別——DuckDB 與 ClickHouse 為一側，SQLite 與 PostgreSQL 為另一側——源自引擎的建構方式，也是觀察全表掃描面板時應先注意之處。
2. **範圍查詢與掃描回答不同問題**，而前者才是回測會提出的問題。上方視窗涵蓋追蹤資料開頭的交易時段；定義視窗的儲存格會印出實際涵蓋的資料列占比。能依時間分割區裁剪，或走訪依時間排序索引的引擎，無需讀取其餘資料即可回答；先掃描再篩選的引擎則做不到。若只依全表掃描排名，就會隱藏這項差異。請留意占比：若視窗涵蓋整份追蹤資料，左側兩個圖表面板量測的就會是同一查詢。
3. **資料匯入速率與持久化反映在同一個數值中，而非分成兩個。** 此處每個寫入時間都在資料可供查詢時結束，因此提早回覆確認的引擎——透過 ILP 的 QuestDB、InfluxDB——不會顯得毫無成本。
4. **每根寫入長條都包含用戶端成本，其中三根能讓你看見部分成本。** PostgreSQL、TimescaleDB 與 InfluxDB 透過每列要求一個 Python 物件的介面存取，而建立這些物件是獨立運算式，可單獨計時。圖表上方的表格列出該時間。未列入的引擎並非沒有用戶端成本：它們的轉換發生在同時執行寫入的呼叫內部，無法分離。因此應將表格視為三個下限，而非對所有引擎的分類。
5. **比較的品質取決於規則。** 對每個引擎而言，上方每個數值都來自一次冷寫入，以及暖快取讀取的平均值。暖讀取會讓所有具有緩衝池的引擎顯得有利；在冷快取或跨網路情境下，壓縮引擎更有優勢。選擇之前，請以自己的資料匯入路徑重新執行。
